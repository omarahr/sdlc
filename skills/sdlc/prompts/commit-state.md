# Committing `.sdlc/` state

Read `gitMode`, `defaultBranch`, `commitFormat` and, in `stack` mode, `runBranch` from `.sdlc/config.json`.

**Stack mode branches.** `sdlc/run-<n>` is the run branch: the tool creates it at bootstrap and pushes it. It never carries product code. `sdlc/M-<n>` is a milestone branch, cut from `runBranch` when that milestone's first slice starts. Slices are cut from it, and their pull requests target it. The milestone's own pull request targets `defaultBranch`. After the milestone PR merges, `state-write.py` advances `runBranch` onto `defaultBranch`. It does so the next time a branch is cut from it. The advance fast-forwards where it can, merges otherwise, and never force-pushes. The next milestone then branches from shipped code. The advance also deletes milestone branches whose work has already shipped, including that one. `sdlc/<milestoneId>-e2e` is cut from the milestone branch. Audit fix slices (`S-fix-<n>`, which belong to no milestone) come from `runBranch`, and their pull requests target `defaultBranch`.

**Slice commit** (your inputs name a slice and your role file says "slice commit"):
1. Be on branch `sdlc/<sliceId>`. If it does not exist, create it. In `stack` mode, cut it from the slice's milestone branch, or from `runBranch` for an audit fix. Otherwise cut it from the default branch's fetched tip: `git fetch origin <defaultBranch>`, then `git checkout -b sdlc/<id> --no-track origin/<defaultBranch>`. When the repo has no remote, cut it from the local `<defaultBranch>` ref instead: `git checkout -b sdlc/<id> <defaultBranch>`. When the slice's `dependsOn` includes a slice in `awaiting-merge`, cut it from that slice's branch instead. Branching from a ref is always allowed: git refuses only *checking out* a branch another worktree holds, never branching from it. The local `<defaultBranch>` ref belongs to the owner's checkout: the run never advances it.
2. `git add .sdlc .gitignore && git commit -m "chore(sdlc): <what> [<sliceId>]"`. Do not push; the integrator ships it with the slice.

**Default-branch commit** (your role file says "default-branch commit"):
- `stack` mode: commit on the milestone branch the slice or milestone in this commit belongs to (`sdlc/M-<n>`). Use `runBranch` when it belongs to no milestone. Your role file names which: a slice's or a milestone's own state goes on that milestone's branch. Work that belongs to no milestone (bootstrap, the audit, an audit fix slice) goes on `runBranch`. Never choose the branch from a milestone's `status`: a milestone's status is `verified` by the time its writer commits. A status-based rule would send that commit to the wrong branch. Then `git add .sdlc .gitignore` and commit `chore(sdlc): <what>`. Do not push: the milestone pull request carries this state. State on `runBranch` is pushed only by an advance that actually moves it. The advance is `state-write.py` merging `origin/<defaultBranch>` in and pushing when that changed the branch. When `defaultBranch` has not moved since the run branch was last advanced, the advance is a no-op and pushes nothing. `origin/sdlc/run-<n>` can then sit behind by several of these commits. That is expected rather than a missed push. There are no `sdlc/state-*` pull requests in stack mode.
- `direct` or `mr` mode: the run works in the run worktree on branch `sdlc/run-<n>`. The owner's checkout holds `<defaultBranch>` — git forbids checking out a branch another worktree holds. That branch is never checked out here. Sync the run branch onto the default branch's tip first: `git fetch origin <defaultBranch> && git merge --ff-only origin/<defaultBranch>`. Skip the fetch when there is no remote. On a merge failure, report it and stop — nothing has changed. Then `git add .sdlc .gitignore && git commit -m "chore(sdlc): <what>"`, and put it on the default branch: `git push origin HEAD:<defaultBranch>`. With no remote, `git update-ref refs/heads/<defaultBranch> HEAD` moves the owner's branch onto the commit instead. Append a `note` log line "your checkout is behind the moved branch: run `git status` (it must be clean), then `git reset --hard <defaultBranch>`" to log.jsonl.
- `pr` mode:
  1. Sync the run branch onto the default branch's tip first, the way the `direct` or `mr` arm above does: `git fetch origin <defaultBranch> && git merge --ff-only origin/<defaultBranch>` (skip the fetch when there is no remote; on a merge failure, report it and stop — nothing has changed).
  2. `git checkout -b sdlc/state-$(date -u +%Y%m%d%H%M%S)`
  3. `git add .sdlc .gitignore && git commit -m "chore(sdlc): <what>"`, then push.
  4. `gh pr create --title "chore(sdlc): <what>" --body "<one-paragraph summary>` followed by a blank line and `🤖 Generated with [Claude Code](https://claude.com/claude-code)"`.
  5. `gh pr checks --watch`. If `gh pr checks --watch` shows nothing, log a `note` line "no CI checks on state PR" before merging. If a check fails, inspect the log with `gh run view --log-failed`. Fix on the same branch. Push, and watch again.
  6. `gh pr merge --squash --delete-branch`, then sync the run branch onto the default branch's tip again, the same way: `git fetch origin <defaultBranch> && git merge --ff-only origin/<defaultBranch>` (with no remote, `git update-ref refs/heads/<defaultBranch> HEAD` instead — the note is already logged).
  7. If required reviews or branch protection block the merge, the PR remains as it is. Append a `state-pr-blocked` line with the PR url to log.jsonl on the default branch's working tree (uncommitted). Return to the default branch.

`.sdlc/STOP` is gitignored and never committed.
